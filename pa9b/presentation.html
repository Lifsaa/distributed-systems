What is a Fractal?

definition a shape with infinite detail at every zoom level
key idea repeat a simple rule millions of times
property self-similar , zoom in and it looks the same again
in nature coastlines, snowflakes, ferns, lightning, blood vessels
in math non-integer dimension , more complex than a line, less than a plane
// the key insight
complexity does not require a complex formula
it emerges from repetition of something very simple
// z = z² + c repeated enough times = infinite detail

The Mandelbrot Set

// discovered by Benoit Mandelbrot, 1980, IBM
plane complex numbers (x = real, y = imaginary)
pixel c = x + y·i , one complex number per pixel
formula z = z² + c , start with z = 0
iterate repeat until |z| > 2 (escaped) or hit limit
escaped color by iteration count , fast = bright
in-set never escapes , drawn black, ~22% of pixels

The boundary between "escapes" and "never escapes" is infinitely complex. That is why zooming in forever keeps revealing new patterns.

Render the Mandelbrot Set on a cluster

for each pixel (x, y):
c = x + y·i
z = 0
while |z| ≤ 2 and iter < max:
z = z² + c
iter++
// color by escape iteration
output high-res image 1600 x 1200 px
bonus deep-zoom animation 72 frames into the set

Every pixel is independent, no pixel needs another's result. That is the key property that makes this a great distributed task.

05 / 10
// 03, why is Ray suitable?

Embarrassingly Parallel

// "embarrassingly parallel" = no coordination needed between tasks
image = 1600 x 1200 pixels = 1,920,000 independent jobs
tile = 64 horizontal bands, each with ~30 rows
task = 1 band per Ray task, so 64 tasks run in parallel
shared = none // no locks, no communication, no waiting

Each band only needs the viewport coordinates and the iteration limit. Workers never talk to each other. The driver just collects the results with ray.get() and stacks them into the final image. This is exactly the kind of workload Ray is designed for.

06 / 10
// 04, how did we implement it?

The entire distributed part is 6 lines

@ray.remote def render_band(viewport, row_start, row_end, max_iter): return compute_band(viewport, row_start, row_end, max_iter) bands = split_rows(viewport.height, tiles=64) futures = [render_band.remote(vp, s, e, iters) for s, e in bands] image = np.vstack(ray.get(futures))

@ray.remote is a decorator, it tells Ray this function can run on any worker. split_rows() divides the image into 64 equal strips. Each strip becomes one .remote() call, which returns a future immediately without blocking. ray.get() waits for all of them and returns the results in order, then np.vstack assembles the strips into the full image.

3.57× faster with Ray

nodes head + worker-1 + worker-2 (5 CPUs total)
tiles 64 // fine-grained, balances the uneven workload

The theoretical max with 5 CPUs is 5x. We hit 3.57x, which is 71% efficiency. The remaining gap comes from Ray scheduling overhead and load imbalance, the deep black interior tiles take many more iterations than the edge tiles. Using 64 fine tiles instead of 16 helps distribute that uneven work more evenly across workers.
